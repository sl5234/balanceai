# Backend decisions

## #1 — 2026-08-20 — External SDK clients use lazy, memoized construction via `functools.lru_cache`, co-located with their service

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #1 (docs/PLAID_INTEGRATION_DECISIONS.md)

**Short description:** Going forward, external SDK clients (Plaid, and any future provider) are constructed lazily and memoized with `functools.lru_cache()` (or `functools.cache`) on a zero-arg factory function — first call builds and caches the client, later calls reuse it — rather than a hand-rolled `global`/`None`-check singleton. The factory stays co-located with the service module that uses it (e.g. `get_plaid_client()` inside `services/plaid.py`), not centralized in a shared client registry — the number of single-purpose external APIs in this codebase doesn't yet justify that extra layer of indirection.

**Short example:** `get_plaid_client()` in `services/plaid.py`, decorated with `@lru_cache`, replacing the "rebuild every call" style used by the existing Tavily/Gemini/OpenAI/Anthropic services.

**Grounded facts:**
- [verified] Existing codebase already has two inconsistent client-construction patterns: `AWSClients` (`dagger/aws.py`) is eager-initialized at server import and cached via explicit `initialize()`/getter methods; the Gemini/OpenAI/Anthropic/Tavily services each build a brand-new SDK client on every call, with no caching.
- [verified] `AWSClients` lives in its own module separate from any one service because it's a shared bootstrap dependency `config.py` itself needs (to KMS-decrypt the other providers' API keys) before those providers' clients can even be built — not because "separate client module" is the general house style.
- [verified] Gemini/OpenAI/Anthropic/Tavily each construct their client inline inside their own `services/<provider>.py` file (`services/gemini.py:19`, `services/openai.py:37`, `services/anthropic.py:33`, `services/tavily.py:6`), not in a separate client module.
- [unverified] User's stated preference: the ideal pattern is "call whenever the client is needed; first call initializes, subsequent calls skip initialization and reuse" — i.e. lazy + memoized, not eager-at-import like AWS and not rebuild-per-call like the other four services.
- [unverified] Agreed in conversation: `functools.lru_cache()` on a zero-arg factory function is the idiomatic mechanism for this, preferred over hand-rolling a module-level `global`/`None`-check singleton.
- [unverified] Agreed in conversation: with only a handful of single-purpose external APIs in this codebase, per-service co-location (client-getter next to the service that uses it) beats a central client registry — the registry's main benefit (one seam for testing/mocking, one consistent pattern) doesn't yet outweigh the added indirection for what's often a few lines of setup per provider.

## #2 — 2026-10-11 — The LLM classifies transactions; journal entries are generated by rule

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #3; #4 (docs/PLAID_INTEGRATION_DECISIONS.md); #1 (docs/product/PRODUCT_DECISIONS.md)

**Short description:** The LLM's judgment lives on the transaction: which account the other side of the entry belongs to, the category, and the counterparty. The user can correct those fields. Journal entries are then generated by a fixed rule from the transaction's amount sign, that account, and the bank account's type — no LLM, and the user never edits them. Why: bookkeeping is meant to be fully managed, a correction is one field instead of two balanced lines, and the debit/credit sides aren't a judgment once the transaction is classified. Cost: a transfer between two of the user's own accounts and a transaction split across several accounts don't fit one classification per transaction and need their own handling.
**Short example:** A −500 dinner on a credit card is classified `non_essential_expense` / `dining` / Nobu. The rule produces: debit `non_essential_expense` 500, credit `accounts_payable` 500 (because the bank account is a credit card). If the user changes it to `essential_expense`, the lines are regenerated.

**Grounded facts:**
- [verified] In today's prompt (`prompts/extract_journal_entry_prompt.py`), the judgment calls are the account, category, recipient, description, and refund-vs-income; the rest (two equal lines, which side, balancing) is a fixed rule the LLM is asked to follow.
- [verified] Today the LLM is never told the bank account's type, and every example in the prompt uses `cash` for the other side, including for credit card purchases.
- [verified] Salary, purchase, refund, card payment, and loan/repayment examples worked through in this conversation all followed from sign + classified account + bank account type.
- [unverified] That most Plaid transactions are simple two-line cases — assumed, not measured.

## #3 — 2026-10-11 — LLM writes journal entries directly and users edit them

**Category:** system (technical)
**Status:** rejected
**One-way door:** no
**Related:** #2; #2 (docs/product/PRODUCT_DECISIONS.md)

**Short description:** Rejected in favor of #2: keeping the LLM pass at the journal entry level (as the code does today) and letting users edit entries to fix mistakes. It would make users keep debit and credit lines consistent and balanced themselves, which contradicts fully managed bookkeeping.
**Short example:** To fix a dinner booked as groceries, the user would have to change the account on one line and the category on both.

**Grounded facts:**
- [verified] The LLM runs once per transaction in either design, so there is no cost difference.
- [verified] There is no per-entry editing today — only replacing a journal's whole entry list through `update_journal`.

## #4 — 2026-10-19 — Transactions with the same description, direction, and account type share one classification

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #2

**Short description:** A transaction's match key is its description (lowercased, spaces collapsed), whether money went in or out, and its bank account type. Transactions with the same match key get the same classification: an already-classified one is copied (the user's wins over the AI's; otherwise the most recent transaction's), and matching unclassified ones are sent to the AI once. Transfers, loan payments, and income never share. Why: the same merchant in the same direction almost always means the same thing, so this saves AI calls without changing answers. Cost: when the same text means different things (a payment app used for different purposes), they all get the first answer until the user corrects them.
**Short example:** Six "Uber" rides on the credit card: the AI is asked once, and all six get non_essential_expense / rideshare / Uber.

**Grounded facts:**
- [verified] In the local sandbox data, 49 transactions have 14 distinct descriptions.
- [verified] Plaid labels some transactions wrongly (Gusto payroll as TRANSFER_OUT), so the no-share categories are based on a label that can be wrong.

## #5 — 2026-10-26 — Two raw transactions are the two sides of one transfer only under a strict rule

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #2, #6, #7, #12

**Short description:** Two raw transactions match as one transfer when they're on different bank accounts, have the same amount with opposite signs, are within 5 days, and each one's counter account equals the other's bank-side account. No AI call. Why: the last check means the two classifications independently agree this is a transfer between these two kinds of account, so unrelated transactions that share an amount never match. Cost: a side the AI misclassified doesn't match, so that transfer is counted twice in balances until corrected.
**Short example:** Checking -900 (counter credit_card_payable) and the card +900 (counter cash) a day later match; a -900 purchase and a +900 paycheck never do.

**Grounded facts:**
- [verified] The AI classified the card side of a card payment wrongly before the prompt fix, so a classification can be wrong on one side.
- [unverified] Transfers between banks usually land within 1–3 business days.

## #6 — 2026-10-26 — Matching on amount and dates alone, without the counter-account check

**Category:** system (technical)
**Status:** rejected
**One-way door:** no
**Related:** #5

**Short description:** Match any two transfer-type transactions with opposite amounts within 5 days, without checking that their counter accounts point at each other. Rejected: a wrong match is harder to spot and undo than a missed one.
**Short example:** Two unrelated $1,000 movements in the same week would match.

**Grounded facts:**
- [unverified] Wrongly matched transfers are harder for a user to notice than unmatched ones.

## #7 — 2026-10-26 — A matched transfer is booked as one entry of the two bank-side lines

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #5, #8

**Short description:** A matched transfer books only each side's bank-side line, each keeping its own date and bank account; both counter lines are dropped. An entry's lines share an entry id. Why: the transfer appears once, so totals per account are exact. Cost: for the days in between, the money looks in transit (it has left one account but not yet reached the other).
**Short example:** Pay the card $900 from checking: credit cash (checking) 900 on 10/20, debit credit_card_payable (card) 900 on 10/21.

**Grounded facts:**
- [verified] Converting each side separately gives four lines, counting the payment twice in both cash and credit_card_payable.

## #8 — 2026-10-26 — Keep all four lines of a matched transfer

**Category:** system (technical)
**Status:** rejected
**One-way door:** no
**Related:** #7

**Short description:** Book both sides of a transfer as separate two-line entries. Rejected: account totals double the transfer (cash and the card's debt each move by twice the payment).
**Short example:** A $900 card payment would lower cash by $1,800.

**Grounded facts:**
- [verified] Spending and income are unaffected by the extra lines; only balances are.

## #9 — 2026-10-26 — A transfer with no visible other side is booked as cash to an unknown account

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #2, #5, #10, #11

**Short description:** A transfer with no partner (the other account isn't linked, or a match is ambiguous) is booked from its one transaction as usual, but its counter line has no bank account: money moved to or from an account we don't track. A payment to an unlinked card stays credit_card_payable. Why: the linked account's balance matches its bank and total cash stays right, since the money is still yours. Cost: an unlinked card's purchases are never seen, so its payable can go negative and spending is understated until the card is linked. Transfers between journals are deferred until business journals are supported.
**Short example:** Chase -2,000 to an unlinked Ally account: debit cash (unknown) 2,000, credit cash (Chase) 2,000.

**Grounded facts:**
- [verified] Tagging both lines with the transaction's own bank account makes them cancel, leaving that account's balance unchanged.
- [verified] The business account list exists but nothing uses it yet.

## #10 — 2026-10-26 — Book a payment to an unlinked card as spending

**Category:** system (technical)
**Status:** rejected
**One-way door:** no
**Related:** #9

**Short description:** Treat a payment to an unlinked card as an expense so spending roughly includes that card. Rejected: once the card is linked its purchases arrive too, and spending double counts.
**Short example:** A $900 Amex payment as non_essential_expense, then $900 of Amex purchases after linking: $1,800 of spending.

**Grounded facts:**
- [unverified] Users link more of their accounts over time.

## #11 — 2026-10-26 — A separate account for money leaving a journal

**Category:** system (technical)
**Status:** rejected
**One-way door:** no
**Related:** #9

**Short description:** Book transfers to an account outside the journal against a new equity account (journal_transfer) instead of cash. Rejected: in real books, money in your own untracked account is still your cash, and an untracked bank account on the counter line already keeps balances right.
**Short example:** Chase -2,000 to Ally would have reduced total cash by 2,000.

**Grounded facts:**
- [verified] In double entry, a move between two of your own bank accounts is cash to cash.

## #12 — 2026-10-26 — Among several matches, the closest date wins; a true tie isn't matched

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #5, #9

**Short description:** Each transaction matches at most once, with the candidate closest in date. When two candidates on different bank accounts are equally close, none of them match; they're booked unmatched and flagged. Why: a wrong pick between identical candidates changes nothing, but between different accounts it misstates both balances. Cost: a true tie needs the user to resolve it.
**Short example:** Checking -1,000 on 10/1, and two savings accounts each +1,000 on 10/2: all three are booked unmatched.

**Grounded facts:**
- [verified] Booked unmatched, totals and each linked account's balance stay right.

## #13 — 2026-10-26 — Book transfers right away and rebook when the other side arrives

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #7, #9

**Short description:** A transfer is booked unmatched as soon as it's classified. When its partner arrives later, the unmatched entry is replaced by the matched one; when a side is removed or reclassified, the matched entry is replaced by unmatched ones. Why: the books are complete at all times, and entries are generated by rule so replacing them is safe. Cost: entries change after they first appear.
**Short example:** Chase syncs Monday (booked to cash, unknown); Ally syncs Thursday (replaced by one matched entry).

**Grounded facts:**
- [verified] Users never edit journal entries (#2), so nothing user-made is lost when one is replaced.

## #14 — 2026-10-26 — Hold transfers unbooked until their other side arrives

**Category:** system (technical)
**Status:** rejected
**One-way door:** no
**Related:** #13

**Short description:** Leave a transfer out of the books for up to 5 days waiting for its partner, then book it matched or unmatched. Rejected: balances are wrong while it waits, it needs a later run to finish, and results depend on the date the run happens.
**Short example:** Chase would be off by $1,000 from Monday until Ally syncs.

**Grounded facts:**
- [verified] Booking runs only when a sync runs, so a waiting transfer could stay out for as long as the user doesn't sync.

## #15 — 2026-10-27 — Match only unmatched transactions

**Category:** system (technical)
**Status:** accepted
**One-way door:** no
**Related:** #12, #13, #16

**Short description:** Matching looks only at unmatched transactions; booked matched transfers are left alone. Why: they stay stable. Cost: a late-classified transaction that would have tied doesn't undo the match.
**Short example:** Checking −1,000 matches savings +1,000; Ally +1,000 is classified a day later and is booked unmatched.

## #16 — 2026-10-27 — Re-match everything in the window

**Category:** system (technical)
**Status:** deprioritized
**One-way door:** no
**Related:** #15

**Short description:** Re-run matching over booked matched transfers too, so the result doesn't depend on arrival order. Deprioritized: it's rare, and it changes entries the user has already seen. A TODO marks the spot in the booking code.

## #17 — 2026-11-02 — Users don't edit entries; only booking writes them

**Category:** product
**Status:** accepted
**One-way door:** no
**Related:** #2

**Short description:** Entries are written only by booking, from classifications. A user corrects a transaction's classification, never an entry. So `update_journal` takes no `entries`.
**Short example:** Uber booked as `non_essential_expense`; the user changes the classification to `essential_expense`, and the entry is rebooked.
